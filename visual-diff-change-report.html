1. Context — why this feature, and why now

SpinZero already has the storage side of a version-control system: every crunch of a KiCad design is content-hashed into a revision (r_…), the raw source is deduped into raw/objects/, and any revision can be re-materialized and re-extracted on demand into a machine-local cache. The history graph (opened from the footer version chip) shows the revision DAG with tags, publishes, and hide/retract.

What was missing is the payoff of keeping all that history: answering “what actually changed between these two revisions?” The version-control plan explicitly leans on this — its merge story is fork-and-surface, never auto-merge (EDA files aren’t 3-way mergeable), and “visual diff shows exactly what each side changed” is the promised fork-resolution UX. Until now, that was a placeholder promise: an earlier compare in the graph was removed per feedback, and the backend command that computes per-file source-hash deltas (diff_revisions) sat unused.

This change implements the designed replacement: compare any two revisions and step through the differences as semantic, human-readable statements — “C14 value 100n → 1µ”, “net /SW1 → /PHASE_A, same 5 pins”, “/VBUS rerouted on In2.Cu (+12 −3 segments)” — each anchored to the canvas so stepping zooms to the affected object. Strictly read-only: the app surfaces differences; a human reconciles in the EDA tool.

2. Intuition — the design in five ideas

① Semantic changeset first, pixels never

The diff is computed over the extracted artifacts (the design.json indexes + the PCB geometry IR), not the raw s-expressions and not rendered images. That means serialization noise (uuid/tstamp churn, reordering) is excluded by construction, and every change is a sentence a reviewer can read. Geometry overlays are the illustration, not the diff.

② The storage model does the heavy lifting

Any revision is materializable (ensure_revision_cache), extraction is byte-deterministic (equal cache keys ⇒ literally identical bundles ⇒ empty diff, instantly), and the per-file source-hash delta prunes the work: a .kicad_sch whose blob hash didn’t change cannot contain a schematic change, so that sheet is skipped; an unchanged .kicad_pcb skips the whole PCB pass. Typically only 1–2 files differ.

③ Matching rules are where “semantic” is earned

Components match by refdes, with re-annotation folding: a removed R12 + added R15 with equal value/footprint and ~equal position collapses to one rename row instead of add/remove noise. Nets match by name, with Jaccard folding: unmatched names whose terminal sets overlap ≥ 0.7 collapse to “net /SW1 → /PHASE_A”. A pin that left one net and joined another gets its own row — the highest-value electrical statement.

④ Copper has no uuids, so identity is a content hash

Each track/via/graphic hashes its tuple (kind, layer name, net name, fixed-point coords, width). A moved track therefore reads as removed+added — which is correct for review — and per-(layer, net) grouping keeps it one row (“rerouted +12 −3”), not fifteen. Zones compare by filled area per (layer, net) with a 1 mm² threshold, because vertex-level fill comparison is refill jitter.

⑤ Side-by-side for schematic, overlay for PCB — by design

Schematic edits move things, so overlaying two sheets is unreadable ghosting — the diff view is two islands, A left / B right, with one shared camera (pan/zoom either side moves both). The PCB, whose copper lives in one fixed board space, gets the classic gerber-diff overlay: onion-skin (removed red / added green over the dimmed base), flicker (A/B blink), and wipe (draggable divider) — shipped in session 2, see §7.

The active revision pins to B

While comparing, the app checks out the newer side (B) as the active revision, so selection, cross-probe and comments keep working and anchor to B. All A-side state lives in a separate diffStore with its own lazy caches — designStore stays single-design, and exiting diff mode is just dropping the store + restoring the previously active revision.

3. What was done — backend (src-tauri/)

  • src-tauri/src/diff.rs — the pure engine. diff_bundles(a, b, source_diff) → DiffDoc: no filesystem, no locks, no clock. Emits the diff.a0 schema exactly as designed in plan §2. Change groups: component, net, sheet, doc (from design.json indexes) + placement, routing, zone, silk, text, outline (from the geometry IR). Every change carries kind (added/removed/modified/renamed/moved), impact (electrical/placement/cosmetic/doc), a one-line title, optional detail, and schematic (sheet + element uuids) and/or PCB (bbox/layers/comp/net) anchors.
  • Determinism as a feature. Every intermediate collection is sorted into a total order before becoming a change; ids (ch_0000…) are assigned by ordinal after the final sort. A test asserts identical inputs serialize byte-identically — matching the codebase’s “determinism is load-bearing” rule.
  • prepare_diff(rev_a, rev_b) command. Ensures both revision caches, short-circuits equal cache keys to an empty doc, serves a cached diff.json on repeat (with labels refreshed — revisions can be renamed), otherwise runs the engine, writes the cache atomically (temp-then-rename), and GCs the diff cache to the newest 8. Returns DiffHandle { doc, path, cache_key_a/b, label_a/b }.
  • read_artifact_from(cache_key, rel_path) command. Reads a metadata-stripped artifact from a specific revision’s cache (validating the key is alphanumeric so it can’t escape the cache root) — this is how the A-side island loads its sheet SVGs while B stays active. Read-only.
  • Pruning wired in. The previously-unused rawstore::diff_source_hashes feeds the engine: hash-identical .kicad_sch ⇒ sheet skipped (reported in sheetsPruned); unchanged .kicad_pcb ⇒ the whole geometry pass skipped. Altium prunes nothing and still diffs the bundles.
  • Storage rules respected. The diff cache lives under project::local_data_root(project_dir)/diffs/ — machine-local, regenerable, never in the synced project folder. No EXTRACTOR_CACHE_EPOCH bump (extractor output untouched). No lock .unwrap(), no panics on fallible paths.
  • 19 fixture unit tests (src-tauri/src/diff/tests.rs): value change, add/remove, re-annotation fold (+ the twin-removal regression), net rename via Jaccard, pin membership move, placement move/rotate/flip, routing grouping, zone threshold, sheet add/remove, title-block change, pruning, determinism, empty diff.

4. What was done — frontend (src/)

  • src/lib/diff.ts — TypeScript mirror of the Rust types (same lockstep discipline as design.ts ↔ design.rs) + pure helpers: grouping (fixed group order, within-group sort by sheet/layer then position), impact + free-text filtering, the PCB-anchor → CommentAnchor adapter (net → comp → bbox region), and the tint-role mapping (removed→red, added→green, modified/renamed/moved→amber).
  • src/stores/diffStore.ts — all comparison state: enterDiff (ancestry-normalizes old→new, pins B active, calls prepare_diff, lands on the first change), exitDiff (drops everything, restores the prior active revision), swap (direction flip, bypassing normalization), focusChange (drives the canvases per anchor), seen-tracking (ephemeral per session, per plan §11), and the lazy A-side sheet-SVG cache. designStore is untouched.
  • History graph — “Compare with…” (pick mode: second click starts the diff, Esc cancels, the source row is marked), “Compare with previous” (nearest present parent; disabled for roots), and a “Compare tips” header button when the DAG has ≥ 2 heads — the fork-awareness moment the VC plan promises.
  • Diff mode chrome — a banner above the canvas (A → B labels + short revision ids, Swap, ✕ exit, “Preparing comparison…” busy state) and a “comparing” state on the footer version chip (click = exit). Diff mode is view-global: schematic and PCB tabs both show it.
  • Changes panel — a second left-rail tab that exists only while comparing (auto-activates on enter, disappears on exit): tree grouped by change group with count badges, Electrical/Placement/Cosmetic filter chips + free-text search, a “Change N of M” stepper (buttons + ←/→, J/K), per-change seen checkmarks + mark-all-in-group, click-to-focus, and an SCH·PCB badge on dual-anchored changes (X cross-probes them between canvases).
  • Side-by-side schematic — the existing <Canvas /> (B, right) is reused unchanged as the camera driver; it publishes its live camera + viewBox + sheet through a small camBridge each animation frame. The new read-only DiffSchematicA island (left) follows that camera every frame and forwards its own pan/wheel back through camBridge.drive, so either pane moves both. Sheets pair by the design’s numbering; an added/removed sheet shows a placeholder. No selection/comments/history on A — deliberately not a fork of Canvas.
  • Tints — the existing SVG-clone highlight idiom, in a dedicated .hl-diff class so the normal highlight cycle never wipes it: the focused change’s uuids are cloned into an overlay coloured by CSS var (--err/--ok/--warn families — no hardcoded colours) over a scrim that dims the rest, with a pulse on focus. B paints red/green/amber; A paints the old state only (red/amber, never green).
  • 29 new Vitest tests — diff.test.ts (20: grouping, ordering, filtering, anchors, tint roles) and diffStore.test.ts (9: enter/exit/ step/seen with mocked IPC).

6. Orchestration & review fixes

The implementation was delegated to two Opus agents (backend first — it defines the wire format — then frontend, briefed with the exact API), each verified with the full test suite. Both outputs were then independently reviewed, which caught and fixed five real bugs before commit:

#BugFix
1Re-annotation fold could drop a removal. The removed-side skip re-derived the fold predicate, so two identical parts (same value/footprint, position unknown) matching one consumed added-part made the second removal vanish. The fold loop records which A-refdes actually paired (folded_a); removals skip by membership. Regression test added (reannotation_fold_keeps_second_identical_removal).
2Cached diff doc could outlive its bundles. prepare_diff served a cached diff.json before ensuring both revision caches — but the frontend immediately reads both sides’ artifacts, and the bundle cache GCs independently (keeps ~8). Both ensure_revision_cache calls now run before the cached-doc path.
3Swap was a no-op. swap() re-entered through enterDiff, whose ancestry normalization immediately re-derived the same old→new direction. enterDiff takes { normalize: false }; swap uses it.
4Exit restored the wrong revision after a swap. Re-entering while already comparing captured the pinned B as “prior active”. The original pre-diff pin is preserved across re-enters; a failed prepare also un-pins back to the previous revision.
5Stepping ignored the filter. The store’s next/prev walked the unfiltered doc while the “Change N of M” header counted the filtered set — stepping could land on hidden changes. The panel owns the walk over its visible sequence (buttons and keys).

7. Session 2 — Phase 2: the GL compare modes

Context. Session 1 shipped the PCB changeset (placement/routing/zone/ silk/outline rows in the Changes panel) but stepping onto a PCB change only landed the camera + the ordinary net/comp highlight. The plan’s §4 rendering — “load both revisions’ geometry into GPU buffers, render each side’s changed-only primitives over a dimmed common base” — was the deferred half. Session 2 ships it.

Intuition — three ideas

① Changed-ness is a per-primitive attribute, not a re-render

Every GPU batch (track capsules, pad SDFs, via annuli, zone/graphic triangles) now carries one extra float, aFlag: 1 = this primitive does not exist on the other side. The fragment shaders gained uDiffPass: pass 1 draws only unchanged primitives faded toward the dim colour (the common base), pass 2 draws only changed ones recoloured flat in uDiffColor. So all compare modes are uniform switches over buffers that are already resident — flicker is literally a per-frame choice of which renderer draws; nothing re-uploads.

② The set-diff is recomputed in TypeScript, deliberately

glDiff.ts hashes each primitive to a string key — kind, layer name, net name, coords fixed-pointed at the extractor’s own 1e-4 mm rounding, width — the same identity rule as diff.rs::hash_prim. It does NOT need to match the Rust hash bit-for-bit: it only compares A-keys against B-keys, both computed by the same TS function. Because both sides are re-extracted at the same EXTRACTOR_CACHE_EPOCH, identical source geometry serializes identically — equality is exact, not fuzzy. The diff is multiset-aware: 3 identical stitching vias vs 2 flags exactly one, not all three.

③ Two renderers, one canvas, one camera

In diff mode PcbGlView builds a second PcbGlRenderer for A’s geometry on the same WebGL2 context (two compact boards resident is fine — plan §4) and keeps the B renderer as the interactive one (hit-test, selection, labels, worksheet all stay B). Onion: B base pass (dimmed) → A changed-only in --err red → B changed-only in --ok green. Flicker: 500 ms A/B blink, Space holds the current side. Wipe: scissor test splits the framebuffer at a draggable DOM divider — A left, B right. Tints resolve from theme CSS vars (never hardcoded), and entering/exiting diff mode keeps your camera.
Why the overlay can be primitive-exact when the changeset rows aren’t. The Changes panel groups routing into one “rerouted +12 −3” row per (layer, net) because a reviewer wants sentences. The GL overlay wants the opposite altitude: exactly the twelve new segments green and the three old ones red, in place. Both read the same identity rule; they just aggregate differently.

8. Session 2 — UUID footprint pairing (and “what happens if a via moves?”)

The bug. A real board had 136 stitching footprints all named STITCH1. The old diff_placement put A’s components in a designator-keyed HashMap — duplicates collapse to one entry — so every B-side STITCH1 was compared against a single arbitrary A instance and the panel flooded with 135 bogus “moved” rows.

The fix, in three layers:

  • Extractor (extract/src/ir.rs): CompDef now carries the footprint’s KiCad uuid — the stable per-instance identity the file format already provides (fp.uuid was parsed all along, just never emitted). This changes geometry.json, so EXTRACTOR_CACHE_EPOCH bumped 18 → 19 — and because prepare_diff runs ensure_revision_cache for both sides at the current epoch, the next comparison automatically re-extracts both revisions with UUIDs present. No manual re-extraction step.
  • Diff engine (diff.rs): GeomComp.uuid (serde(default), so old cached JSON still parses) and diff_placement now pairs instances by UUID first — a shifted STITCH1 is one accurate row; its 135 unchanged siblings emit nothing; and a re-annotated part (same uuid, new refdes) still pairs correctly.
  • Fallback for uuid-less instances (legacy caches, Altium): a duplicate-safe per-designator pass — exact-position instances consume each other first (an unmoved duplicate can never pair with a moved one), then the leftovers zip in sorted-position order. Surplus instances on one side emit nothing (add/remove is the component diff’s job). Never the old first-instance collapse.

So: what happens if a via’s position changes?

Nothing about the UUID fix applies — and that’s correct. A via is copper geometry, not a footprint: it has no designator and (in the IR) no uuid. Its identity is the content hash of ("via", layer name, net name, x, y, size) — one entry per copper layer the via spans.

Move a via and, on each spanned layer, its old hash disappears from A’s set and a new hash appears in B’s. Two effects:

  • Changeset: the (layer, net) routing bucket gains +1 −1, so the existing “/GND rerouted on In2.Cu (+1 −1 segments)” row absorbs it — or, if only the via moved, that row IS the change. One row per affected (layer, net), never a flood, because grouping — not pairing — is what bounds routing noise.
  • GL overlay: the via is flagged on both sides — its annulus paints red at the old position (from A’s buffers) and green at the new one (from B’s): the classic gerber-diff read of “this copper is gone, that copper is new”.

Contrast with the footprint case: components DO have stable per-instance identity (the uuid), so for them remove+add would be wrong and pairing is right. Copper has no such identity, so remove+add is the honest statement. Same design question — “what is this object’s identity across revisions?” — two different, deliberate answers.

9. Session 2 — the HistoryGraph setState-in-render crash

Symptom (in the logs since 04:55, i.e. pre-dating the diff-colour work): “Warning: Cannot update a component (Toaster) while rendering a different component (HistoryGraph)”, recurring, eventually tripping the ErrorBoundary when the version-history overlay opened.

Root cause — two dominoes:

  • Domino 1 — a conditional hook. The “Compare tips” work added a tips useMemo after HistoryGraph’s if (!open) return null early return. While the overlay was closed the memo never ran; the render that opened it executed one more hook than the previous render — React throws “Rendered more hooks than during the previous render” mid-render.
  • Domino 2 — the crash reporter reacting inside the render phase. In development React replays render errors through a guarded callback that dispatches the window error event synchronously, still inside the render phase. crashReporter’s global handler caught it and immediately pushed a toast — a zustand set on the store the Toaster subscribes to — which IS the “cannot update Toaster while rendering HistoryGraph” warning. The stack pointed at HistoryGraph line 34 (the hook region), which made it look like the graph itself was pushing toasts; it never was.

Fix (a): the tips memo is hoisted above the early return, with a comment explaining the hook-order constraint — the throw is gone, so the overlay opens cleanly. Fix (b), defence-in-depth: crashReporter.report now defers its toast push by one macrotask (setTimeout(…, 0)) so no future render-phase error can cascade into a second setState-in-render; the backend log write stays synchronous so nothing is lost if the webview dies.

The durable lesson: in this codebase every hook must sit above any early return (React’s rules-of-hooks), and anything reachable from a global error handler must be render-phase-safe — it can run at ANY moment, including mid-render. The toast push was the only violator; ipc.logError (fire-and-forget promise) was already safe.

12. Quiz — do you understand this change?

16 questions (Q1–10 session 1, Q11–16 session 2), pass mark 12. Answers are graded locally in this page; explanations appear after grading.

1. Where is the diff computed, and over what data?

The engine (src-tauri/src/diff.rs) is a pure Rust function over the two extracted bundles. Diffing extracted artifacts (not s-expressions) excludes uuid/tstamp/reordering noise by construction; pixels were explicitly rejected.

2. Two revisions turn out to have equal extraction cache keys. What does prepare_diff do?

Extraction is byte-deterministic (guarded by a test on main), so equal cache keys ⇒ identical bundles ⇒ the diff is provably empty. This is intuition idea ②.

3. Where does the computed diff.json live, and why there?

Hard project rule: never write regenerable data into the project folder (a sync should never copy it). It’s keyed by blake3 of the two cache keys and GC’d to the newest 8.

4. A track was dragged to a new position on In2.Cu. How does the changeset express that?

Copper identity is a content hash of (kind, layer name, net name, fixed-point coords, width) — a moved track is genuinely “this copper is gone, that copper is new”, and per-(layer, net) grouping keeps it one readable row. Nearest-neighbour pairing is noted in the plan as a possible later refinement.

5. What folds a removed net + an added net into a single “renamed” row?

Names are matched first; for unmatched names, pin-set overlap (Jaccard ≥ 0.7, greedy best-first with deterministic tie-breaks) folds remove+add into “net /SW1 → /PHASE_A, same 5 pins”. Below threshold they stay separate.

6. While a comparison is active, which revision is the app’s active (checked-out) one, and why does it matter?

The active revision pins to B for the duration; the A side is read-only and lives entirely in diffStore (loaded via read_artifact_from with A’s cache key). Exit restores the pre-diff revision.

7. Why does the schematic diff default to side-by-side rather than an overlay, while the (future) PCB overlay is fine?

Per-view defaults are the plan’s core §4 decision: opposite geometry stability. The two schematic islands share one camera so they stay comparable; the PCB onion-skin/flicker/wipe modes are the deferred phase-2 rendering.

8. What does the visual diff do about merging two forked revisions?

Explicit non-goal, inherited from the VC plan: EDA files aren’t 3-way mergeable, so the model is fork-and-surface. “Compare tips” exists precisely to make a fork loud and diffable.

9. What prunes the diff engine’s work before any semantic comparison runs?

The previously-unused diff_revisions source-hash delta became the pruning front-end — a file whose blob hash didn’t change can’t contain a change. Pruned sheets are reported in sheetsPruned. (The footer’s git hash is NOT revision identity.)

10. Why couldn’t Swap just call enterDiff(b, a) as originally written?

Review fix #3: normalization (ancestry, then timestamp fallback) is exactly right for the initial pick — and exactly wrong for an explicit flip. The same review also preserved the original pre-diff revision for exit-restore across swaps (fix #4).

11. Why did 136 STITCH1 footprints flood the Changes panel with “moved” rows, and what is the fix’s pairing key?

Designators aren’t unique per instance; the uuid is. The extractor now emits CompDef.uuid (from fp.uuid), and diff_placement pairs by it first. Uuid-less instances (legacy caches, Altium) use exact-position matching within a designator group, then sorted-order zipping — never the first-instance collapse.

12. A via’s position changes between revisions. What does the diff say?

A via is copper, not a component: no designator, no uuid. Its identity is the content hash ("via", layer name, net name, x, y, size) per spanned layer, so a move is remove+add, absorbed into the per-(layer, net) routing bucket. The UUID fix changes footprint pairing only — deliberately.

13. Adding uuid to CompDef required bumping EXTRACTOR_CACHE_EPOCH. Why does the diff then work on OLD revisions without any manual re-extraction?

Epoch-in-the-cache-key is the extractor’s self-invalidation mechanism (the “bump on ANY output change” rule). Both diff sides are always materialized at the current epoch, which is also why the two bundles are schema-identical by construction. The serde-default fallback exists for Altium (no KiCad uuids), not for stale caches.

14. How do the GL compare modes get per-primitive “changed” information to the shaders?

Mask textures are net/comp-granular — a whole changed net would tint even its unchanged segments. The flag attribute is primitive-exact, and because it’s an attribute + a uniform, onion/flicker/wipe are all draw-call permutations over the same resident buffers (no geometry rebuild per frame). Pixel XOR was rejected with the rest of raster diffing.

15. Why is it safe for glDiff.ts to compare coordinates with exact string keys instead of a distance tolerance?

Same argument as the Rust engine’s hash (plan §2 “hashing is exact, not fuzzy”): byte-deterministic extraction + 1e-4 rounding at emit time means equality is the right test, and layer/net indices are dereferenced to names so differing index tables can’t split identical copper.

16. The “Cannot update Toaster while rendering HistoryGraph” warning — what was actually pushing a toast during render?

HistoryGraph never pushed a toast. The tips useMemo below the early return changed the hook count when the overlay opened → React threw mid-render → dev-mode error replay dispatched the window error event synchronously → crashReporter’s toast push became the setState-in-render. Fixes: hoist the memo (root cause) AND defer the reporter’s toast by a macrotask (class of bug).
